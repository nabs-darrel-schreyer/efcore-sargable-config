## Details

### 1. ESC004-blanket-convention - blanket varchar convention forces a real Unicode column to varchar

- **Location:** `samples/EfSargable.Sample/Bad/BadConventionDbContext.cs:13` (`BadConventionDbContext.ConfigureConventions`, affecting `Translation.Text`)
- **What's wrong:** `ConfigureConventions` applies `AreUnicode(false).HaveMaxLength(256)` to every `string` property in the context. `Translation.Key` is never overridden either, but it happens to match `schema.json` (`varchar(256)`, indexed). `Translation.Text` has no Fluent override in `OnModelCreating` (only `e.HasIndex(t => t.Text)` is called, which does not set type/length/Unicode), so it also inherits the convention: effective mapping `varchar(256)`. The real column is `nvarchar(400)`, indexed.
- **Why it hurts:** This is not just a scan risk. Round-tripping real Unicode `Text` values through a `varchar(256)` parameter/column view truncates at 256 characters and converts any non-Latin1 character to `?` (mojibake / silent data loss), and comparisons against the real `nvarchar(400)` column still force `CONVERT_IMPLICIT` on the column. Pre-convention configuration beats data annotations, so this is easy to miss in review.
- **Evidence and confidence:** Static only - derived by resolving the effective mapping precedence (`ConfigureConventions` -> no Fluent override for `Text`) against `schema.json`'s `dbo.Translations.Text` row (`nvarchar`, length 400, indexed). Candidate; confirm with `db.Model` dump and an actual plan/round-trip test.

**Before**

```csharp
protected override void ConfigureConventions(ModelConfigurationBuilder builder)
{
    builder.Properties<string>().AreUnicode(false).HaveMaxLength(256);
}

protected override void OnModelCreating(ModelBuilder b)
{
    b.Entity<Translation>(e =>
    {
        e.ToTable("Translations");
        e.Property(t => t.Key);
        e.HasIndex(t => t.Key);
        e.HasIndex(t => t.Text);
    });
}
```

**After**

```csharp
protected override void OnModelCreating(ModelBuilder b)
{
    b.Entity<Translation>(e =>
    {
        e.ToTable("Translations");
        e.Property(t => t.Key); // convention's varchar(256) still correct here
        e.HasIndex(t => t.Key);
        e.Property(t => t.Text).HasMaxLength(400); // override: real column is nvarchar(400)
        e.HasIndex(t => t.Text);
    });
}
```

- **How to verify:** dump `db.Model.GetEntityTypes()` effective `GetColumnType()` for every string property and diff against `INFORMATION_SCHEMA.COLUMNS`; add a round-trip test inserting a non-Latin1 string (e.g. `"café"`) into `Text` and assert it comes back unchanged; capture the actual plan for a `Text =` lookup and confirm no `CONVERT_IMPLICIT` on the column.

### 2. ESC009-implicit-conversion - varchar column converted to int

- **Location:** `samples/EfSargable.Sample/Bad/BadPredicates.cs:29` (`BadPredicates.NumberVsVarchar`, `PredicateDbContext.Account.AccountNumber`)
- **What's wrong:** `Convert.ToInt32(a.AccountNumber) == 12345` converts the indexed `varchar(20)` column (`Account.AccountNumber` is mapped `IsUnicode(false).HasMaxLength(20)` in `PredicateDbContext`, matching `schema.json`'s `dbo.Accounts.AccountNumber`) to `int` before comparing.
- **Why it hurts:** `CAST(AccountNumber AS int)` on the column defeats the index (scan with a computed residual predicate), and `Convert.ToInt32` throws `FormatException` for any row whose `AccountNumber` is not purely numeric (e.g. an alphanumeric account code) - a correctness/availability bug, not just a performance one.
- **Evidence and confidence:** Static only - mapping for `AccountNumber` is confirmed correct (matches schema), so this is purely a predicate shape issue (`other-cause`); no mapping fix applies. Candidate for the scan; the exception risk is a logical certainty from the code shape, not something that needs a plan to confirm.

**Before**

```csharp
public static IQueryable<Account> NumberVsVarchar(PredicateDbContext db) =>
    db.Accounts.Where(a => Convert.ToInt32(a.AccountNumber) == 12345);
```

**After**

```csharp
public static IQueryable<Account> StringVsVarchar(PredicateDbContext db) =>
    db.Accounts.Where(a => a.AccountNumber == "12345");
```

- **How to verify:** run both versions against a row whose `AccountNumber` is non-numeric to confirm the before-version throws and the after-version does not; capture the actual plan on `IX_Accounts_AccountNumber` and confirm Index Seek with no residual predicate.

### 3. ESC012-closed-date-range - closed end date misses rows after midnight

- **Location:** `samples/EfSargable.Sample/Bad/BadPredicates.cs:38` (`BadPredicates.ClosedEndDate`, `PredicateDbContext.Sale.OrderDate`)
- **What's wrong:** `s.OrderDate >= new DateTime(2025,1,1) && s.OrderDate <= new DateTime(2025,12,31)` - `new DateTime(2025,12,31)` means midnight (`00:00:00`) on 31 Dec, so any sale recorded later that day (e.g. `2025-12-31 14:30:00`) is excluded even though it is clearly "in range".
- **Why it hurts:** This is sargable (plain comparisons on a bare column) but silently returns fewer rows than intended - a correctness bug that will not show up as an error, only as under-counted results.
- **Evidence and confidence:** Static only - the boundary literal has a zero time component and `OrderDate` is a `DateTime` (not a date-only type), so the gap is certain from the code alone; no plan needed to confirm the correctness issue, though a plan would also show this is sargable already.

**Before**

```csharp
public static IQueryable<Sale> ClosedEndDate(PredicateDbContext db) =>
    db.Sales.Where(s => s.OrderDate >= new DateTime(2025, 1, 1) && s.OrderDate <= new DateTime(2025, 12, 31));
```

**After**

```csharp
public static IQueryable<Sale> YearAsHalfOpenRange(PredicateDbContext db) =>
    db.Sales.Where(s => s.OrderDate >= new DateTime(2025, 1, 1) && s.OrderDate < new DateTime(2026, 1, 1));
```

- **How to verify:** add a row with `OrderDate = 2025-12-31 23:59:00` and assert it is included; compare row counts before/after the fix for the same calendar year.

### 4. ESC001-unicode-mismatch - unconfigured indexed string compared against a varchar column

- **Location:** `samples/EfSargable.Sample/Bad/BadDbContext.cs:18` (`BadDbContext.Customer.Email`)
- **What's wrong:** `e.Property(c => c.Email)` has no `IsUnicode`/`HasMaxLength` call, and the property is indexed (`e.HasIndex(c => c.Email)` on the next line), so EF Core's default convention maps it to `nvarchar(450)`. `schema.json` says the real `dbo.Customers.Email` column is `varchar(256)`, indexed.
- **Why it hurts:** `nvarchar` has higher data type precedence than `varchar`, so SQL Server converts the **column** (`CONVERT_IMPLICIT(nvarchar(256), [Email], 0)`), defeating the index on an equality lookup that is presumably selective and hot (customer email lookup).
- **Evidence and confidence:** Static only - effective mapping (`nvarchar(450)`, derived from the "no config + indexed" convention per detection.md) differs from `schema.json`'s `varchar(256)`. Candidate; not yet confirmed with an actual plan.

**Before**

```csharp

e.HasIndex(c => c.Email);
```

**After**

```csharp
e.Property(c => c.Email).IsUnicode(false).HasMaxLength(256);
e.HasIndex(c => c.Email);
```

- **How to verify:** `ToQueryString()` on an `Email ==` lookup should show a plain `varchar`/`AnsiString` parameter, not `N'...'`; actual plan should show Index Seek with no `CONVERT_IMPLICIT` warning; compare logical reads before/after.

### 16. ESC003-length-mismatch - varchar(max) vs. the real varchar(20) column

- **Location:** `samples/EfSargable.Sample/Bad/BadDbContext.cs:35` (`BadDbContext.Order.Reference`)
- **What's wrong:** `e.Property(o => o.Reference).IsUnicode(false)` sets `Unicode` correctly (matching the real `varchar` column) but sets no `HasMaxLength` and there is no `HasIndex(o => o.Reference)` call in `BadDbContext`, so the property is not treated as indexed by EF's own model and defaults to `varchar(max)`. `schema.json` says the real `dbo.Orders.Reference` column is `varchar(20)`, indexed.
- **Why it hurts:** This is a length-only mismatch (type already agrees, so there is no column-side `CONVERT_IMPLICIT`): `varchar(max)` cannot be used as an index key and inflates memory grants, but it is not itself a correctness risk here because the model length (`max`) is longer, not shorter, than the real column (no truncation risk on write). Separately, `BadDbContext`'s model does not declare an index on `Reference` at all, even though the real column has one - a migration/documentation gap worth closing alongside the length fix.
- **Evidence and confidence:** Static only - candidate, low severity (length-only, no correctness risk).

**Before**

```csharp
e.Property(o => o.Reference).IsUnicode(false);
```

**After**

```csharp
e.Property(o => o.Reference).IsUnicode(false).HasMaxLength(20);
e.HasIndex(o => o.Reference);
```

- **How to verify:** diff `GetMaxLength()` against `schema.json`/`INFORMATION_SCHEMA.COLUMNS`; confirm the EF model's index declarations match `sys.indexes` for this table.

### 17. ESC010-or-across-columns - OR across two different columns

- **Location:** `samples/EfSargable.Sample/Bad/BadPredicates.cs:32` (`BadPredicates.OrAcrossColumns`, `Person.FirstName`/`Person.LastName`)
- **What's wrong:** `p.FirstName == name || p.LastName == name` compares the same parameter against two different indexed columns joined by `OR`.
- **Why it hurts:** This can force a scan if the optimiser does not union the two index seeks, but per the skill's verified SQL Server 2022 observations the optimiser frequently combines two single-column seeks itself (index union/merge join) when both columns are indexed - so this is reported at low severity, not assumed to need a rewrite.
- **Evidence and confidence:** Static only - candidate, low severity. Must be confirmed with the actual plan before rewriting to `UNION`, since the rewrite is not always a net gain.

**Before**

```csharp
db.People.Where(p => p.FirstName == name || p.LastName == name);
```

**After (only if the plan confirms a scan)**

```csharp
db.People.Where(p => p.FirstName == name).Union(db.People.Where(p => p.LastName == name));
```

- **How to verify:** actual plan first - look for an existing index union/merge join (two seeks) before changing the query; compare logical reads between the `OR` version and the `UNION` rewrite.
